# 阶段8执行路径成本审计（2026-11-04）

对象：phase8_small_count_20261104_101201_154809532；本轮仅离线读取真实记录和运行合成SDK调用计数，不连接IoTDB、不修改优化算法或生产路径。

## 结论

E0/E1/E2的DecisionExecutionService与E3/E4/A1/A2的Orchestrator存在基础设施优化不对称：后者run使用request_scope和store_session，前者没有。请求内解析复用及SQLite连接复用只在一侧生效。现有比较可描述两个实际路径的总耗时，**不能隔离四Agent/学习的净收益，公平性验收存在明确缺项**。

E4比E3慢的差额主要落在决策阶段；两者具有相同基础设施路径和相同策略/命中，本轮没有学习带来更好动作的证据。不是数据库执行变慢，也不是留出阶段进行模型训练。

Adapter是客户端调用/读取/缓存返回计时，不是服务端纯执行。executor_other包含验证等工作，不能全部命名为解析。remaining包含请求前置准入、初始解析、数据库准备/持久化和路径外围成本；旧服务没有细分计时，不能硬拆成SQLite毫秒或GC毫秒。

E3的第二次连接来自Lane.request计时结束后的experience读取；workflow计时内为1次连接。上述诊断只在临时合成对象上包装已有机制，没有保存生产代码修改、删除验证或更改策略。证明重复工作结构不同，不证明每次重复工作的真实毫秒代价。

对应代码：execution/service.py的run无请求scope/session；orchestration/orchestrator.py的run有两装饰器；request_memo.py实现请求内缓存及会话计时；storage/sqlite.py在会话外每操作打开/提交/关闭，会话内连接复用但每操作仍提交。两者初始化/查询/决策/执行/报告的调用路径不同。

## 计时口径审查

最终比较应继续使用RequestRecord.elapsed_ns完整外层计时。execution.end_to_end_ms在service中截于record_execution_report之前，在Orchestrator中截于监控、学习、trace等阶段之前，不能直接跨路径比较，也不能代替完整E2E。

原真实日志所有非Native组动作和命中数量相同。E4相对E1的优势受基础设施不对称混杂；E4相对E3的负收益仍是当前同路径对照的重要结果。不能从旧结果扣除估算开销来生成“修正后收益”，也不能因为analysis_qualified=true便认定组间因果比较公平。
